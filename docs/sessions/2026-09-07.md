Two real bugs surfaced from the first real-world use — both fixed this
session (`root` commits):

### 1. `parseList.ts` fieldCount bug — photo icons missing on the public list

- **Symptom**: the owner linked photos in /settings/ and the settings UI
  showed them linked correctly, but the public home page showed NO camera
  icons on those checked items (and the item text linked to a broken URL
  like `https://example.com|08`).
- **Cause**: `parseList.ts` (server-side, used to render the public site)
  called `parseLines(..., 4, ...)` — fieldCount=4. Every row in
  `data/list.env` now has 5 columns (`NN|checked|text|link|photo`), so the
  parser merged the 5th (photo) field into the 4th (link). Result:
  `link = "https://example.com|08"`, `photo = ""`. The `/settings/` page
  uses a *different* client parser (`settingsClient.ts`) that splits on all
  fields correctly — which is why settings "worked" and the public site
  didn't.
- **Why fieldCount was 4**: a forward-compat migration hack from when only
  3 of 92 rows had the photo column (see DECISIONS 2026-08-29). The extra
  fields were merged into the last required one so old 4-column rows still
  parsed. Once all 100 rows carry 5 columns, that hack corrupts every row.
- **Fix**: `fieldCount=4` → `fieldCount=5` in `parseList.ts`. Verified all
  100 rows are 5-column first.
- **Lesson**: two parsers (server `parseList.ts` and client
  `settingsClient.ts`) must agree on the schema. When one was "future-
  proofed" with fieldCount=4 and the other wasn't, they drifted silently.

### 2. Camera icon rendered but was not clickable

- **Symptom**: after fix #1 deployed, the camera icons appeared on items
  39/72/81 — but clicking an icon did nothing.
- **Cause**: the icon was a decorative `<span class="list-item__photo-icon"
  aria-hidden="true">`. Only the item *text* was wrapped in the `<a>` to
  `/gallery/#NN`. Clicking the icon was a no-op.
- **Fix**: made the icon an `<a href="/gallery/#NN">` mirroring the
  existing video-icon pattern, with an `aria-label="查看照片 #NN"`. CSS:
  the icon now uses the coral accent + hover fade so it reads as
  interactive instead of decorative.
- **Lesson**: verifying that an element *renders* in the built HTML is not
  enough — verify it *does the thing*. For interactive elements check the
  generated markup has the real behaviour (`<a href=…>`, a handler, the
  right anchor), not just that it "appears". This rule is now in
  `AGENTS.md` §"Things to never do".
